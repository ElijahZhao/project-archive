# 并发 CI 工程：为什么测试从 0 长到 28 项

## 一开始没有 CI

这个项目刚起步时，只有部署：push 到 main，GitHub Actions 自动发到 Pages。没有测试。改东西靠"改完看一眼"，运气成分很大。

转折点是那个缩略图 bug——发布脚本自己删掉了自己生成的缩略图，首页裂图。我修了 3 行代码，但意识到一个问题：**这种错我下次还会犯**。单靠细心守不住流程。

## 测试是怎么长出来的

不是一次性设计的，是一张卡、一个坑、一个坑喂出来的。现在 `gallery-check` 在每次 push 时跑 **28 项测试**：

| 组 | 测什么 |
|---|---|
| 配置 schema | 每张卡的字段结构合法，缺字段直接失败 |
| manifest 一致性 | cards.json 和实际文件对得上，不悬空 |
| i18n 覆盖 | 新加的标签必须有中英词条，缺了不让过 |
| importmap 幂等 | 前端模块映射改写两遍不重复 |
| 缩略图 | 每张卡必须有真实缩略图（防裂图复发） |
| 资产验证 | GLB 有效、vendor 就位、引用不 404 |
| prompt 构建 | 生图 prompt 模板正确组装 |
| preflight 门禁 | 出卡前置检查（模型缓存、密钥、依赖） |

外加一个**画廊体检**：77 张卡全量过一遍资产存在性。这活儿本来应该人肉做，现在 CI 每 push 都替我做。

## 并发的坑

项目做到后面，一次要渲染好几张卡。工作流并发跑的时候出过问题：两个任务同时写同一个项目目录，互相踩。后来给 workflow 加了并发组——同一时刻只允许一个渲染任务跑，后来的排队等。

听起来像退步（不能并行不是更慢吗？），但实际收益大：**确定性**。渲染是写文件的重活，撞车一次浪费的是整批重跑，排队等反而稳。

## 一个判断

测试的多少不是 KPI。28 项是因为"这 28 类错真的发生过或很可能发生"。每加一类错，就补一条测试把它钉死，项目才敢越改越大。

没 CI 的爽是暂时的，有 CI 的慢是划算的。
